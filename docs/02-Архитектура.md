# Архитектура

Обновлён: 23.09.2026
Версия схемы данных: 2 в релизе (долги, Р-30); 3 — заметки к капиталу, Этап 4 (Р-36)

**Состояние документа.** Модель окончательная целиком. Форма записи учёта решена по выгрузкам банков в части А Этапа 0 (Р-12); типы долгов решены по образцу «Верните Деньги» в начале Этапа 3 (Р-30, Р-31) и приходят первой миграцией схемы.

## Стек

- **Vite + React + TypeScript**, `strict` и `noUncheckedIndexedAccess` — настройки ядра, `tsconfig` — `extends: "./src/shared/tsconfig.base.json"`
- Роутинг через хеш (`#/month`), `HashRouter` — на GitHub Pages обычные пути дают 404 при обновлении страницы
- Сайт живёт по `/Zloty/` (Р-10): `base` в `vite.config.ts` равен имени репозитория, с ним согласованы `start_url`, `scope`, `id` манифеста, пути иконок и `navigateFallback`. Неверный `base` даёт зелёную сборку и белую страницу
- Стили — обычный CSS: каркас ядра `src/shared/styles.css`, поверх — свой `src/styles.css` с акцентом
- Хранилище — IndexedDB, синхронизация — приватный репозиторий GitHub; механика — ядра
- Service worker — `startWorker` ядра, свой — только тема напоминания; сборка `injectManifest` через `familyVite`
- **Ядро — `FamilyCore`, подмодулем в `src/shared`** (Р-03)
- Бэкенда нет. Платформа — PWA

## Два репозитория

| Репозиторий | Что внутри | Видимость |
|---|---|---|
| `Zloty` | исходники, сборка, GitHub Pages | публичный |
| `ZlotyData` | JSON-файлы данных | приватный |

Pages для приватного репозитория требуют платного тарифа, поэтому код публичный. Секретов в нём нет по определению. Токен вводится руками в настройках и живёт только в браузере; у каждого устройства свой.

## Модель данных

`Base` — из ядра (`shared/core/model.ts`), договор семьи: `id` (ULID), `updatedAt`, `deleted?`. Своей не заводится.

### Деньги — решено (Р-04)

```ts
// Сумма — целое число в минимальных единицах валюты: 123456 RUB = 1 234,56 ₽.
// Сумма всегда положительная: направление даёт `kind` операции (Р-12).
type Money = {
  amount: number               // целое, неотрицательное
  currency: CurrencyCode
}

// Код валюты: 'RUB', 'USD', 'BTC', 'USDT'. Что он значит — в справочнике currencies.
type CurrencyCode = string

// Курс на дату: 1 from = rate to. Дробный — законно: пересчёт не хранится.
type Rate = Base & {
  date: string                 // ГГГГ-ММ-ДД
  from: CurrencyCode
  to: CurrencyCode
  rate: number
  source: 'manual' | 'import' | string   // публичный источник — своим именем: 'currency-api' (Р-38)
}
```

- **Пересчёт — чистая функция**, результат округляется при показе и нигде не хранится
- **Какой курс:** операция — на дату операции; снимок в капитале — **на дату капитала** (Р-40, уточняет Р-04, п. 5): устаревает количество, а не цена. Нет курса на дату — ближайший более ранний не старше `RATE_MAX_AGE_DAYS`; нет и такого — позиция вне итога и названа числом
- **Нет прямого курса — через одну промежуточную валюту** (Р-37): BTC→USD→RUB, основание называет оба курса; прямой, если есть, главнее
- **Курс руками:** та же пара на ту же дату правится, а не заводится второй; обратная пара на ту же дату — отказ
- **Единица показа** — свойство записи валюты: BTC хранится в сатоши, показывается в mBTC
- **Базовая валюта и вторая валюта показа** — свойство данных, синхронизируются: запись `profile`, ниже (Р-12). Базовая не выбрана — итоги в первой заведённой валюте, экран называет основание (Р-41)

### Справочники

```ts
// Валюта — запись, а не строка в коде: новая заводится из интерфейса (Р-12).
type Currency = Base & {
  code: CurrencyCode           // 'RUB', 'BTC', 'USDT'
  name: string                 // «Рубль», «Биткойн»
  decimals: number             // знаков в минимальной единице: 2 у рубля, 8 у BTC; больше 8 не бывает
  unit?: { name: string; factor: number }   // единица показа: mBTC — { name: 'mBTC', factor: 100000 }
  order: number
}

// Где лежат деньги. Одна валюта на счёт (Р-05).
// Счёт — банк целиком, а не карта и не вклад (Р-12): выписка банка ложится
// на один счёт, движения внутри счёта не записываются.
type Account = Base & {
  name: string                 // банк, наличные, брокерский счёт, кошелёк
  currency: CurrencyCode
  kind: 'savings' | 'investment'   // сбережения / вложения (Р-05)
  ledgerOnly?: boolean         // счёт истории: операции на него не загружаются (Р-12)
  loadedThrough?: string       // ГГГГ-ММ-ДД, по какое число доведена выписка: конец сошедшейся
                               // сверки, записанный импортом; назад не откатывается (Р-26)
  archived?: boolean
  order: number
}

// За что потрачено или откуда пришло. Расходные и доходные — разные (Р-05).
type Category = Base & {
  name: string
  side: 'expense' | 'income'
  archived?: boolean
  order: number
}

// Регулярная — шаблон, который сам ничего не пишет (Р-06).
type Recurring = Base & {
  name: string                 // «Связь», «Интернет», «Страховка ОСАГО»
  categoryId: string
  accountId?: string
  expected: Money
  every: { months: number }    // 1 — раз в месяц, 12 — раз в год, N — раз в N месяцев
  from: string                 // ГГГГ-ММ, с какого периода действует
  to?: string                  // ГГГГ-ММ, по какой; нет — действует
  order: number
}

// Настройки учёта, общие для всех устройств (Р-12). Одна запись; единственность
// держат код и тест — тип её не гарантирует.
type Profile = Base & {
  baseCurrency: CurrencyCode   // в ней считаются итоги
  showCurrency?: CurrencyCode  // вторая валюта капитала
  periodStartDay?: number      // 1 — календарный месяц; иное — свой отчётный период, экран позже
  savingsGoal?: number         // цель нормы сбережений, доля: 0.2 — «откладывать 20%»
}
```

Id — ULID у всего, включая справочники: это договор семьи (`shared/core/model.ts`). Переименование категории id не меняет, история к ней привязана по id. Сопоставление по названию при импорте — механика ядра, без учёта регистра и лишних пробелов (`shared/core/importing.ts`).

### Записи учёта (Р-02, Р-12)

```ts
// Операция — или итог периода там, где операций нет (Р-02).
type Entry = Base & {
  kind: 'expense' | 'income' | 'transfer'   // transfer — между своими счетами: не расход и не доход
  accountId: string            // откуда деньги ушли или куда пришли; у transfer — откуда
  money: Money                 // всегда в валюте счёта, всегда положительная
  date?: string                // ГГГГ-ММ-ДД — операция
  time?: string                // ЧЧ:ММ, если банк его дал; входит в ключ
  period?: { from: string; to: string }     // итог периода вместо даты
  categoryId?: string          // у transfer — нет; у итога периода — необязательна (Р-12)
  toAccountId?: string         // у transfer; может быть неизвестен — «второй счёт не указан»
  special?: boolean            // особая: во всех расходах есть, в обычном месяце нет (Р-05)
  recurringId?: string         // от какой регулярной (Р-06)
  for?: string                 // ГГГГ-ММ — «за какой период», только для блока «Регулярные» (Р-06)
  bankText?: string            // исходная строка выписки, как пришла (Р-12)
  ext?: string                 // внешний ключ импорта: записывается один раз и не меняется
  note?: string                // комментарии таблицы — сюда
  refs?: string[]              // связь с тратой комнаты, долгом или возвратом: в поток идёт доля (Р-31)
}
```

- **`ext`** — `<счёт>:<код банка>`, если банк его дал; иначе `<счёт>:<дата>:<время>:<сумма>:<нормализованное описание>:<номер среди одинаковых за день>`. Совпал — операция пропущена как повтор
- **Итог периода** держит `period` вместо `date`; счёт обязателен, категория — нет. В файл он ложится по `period.to`
- **По месяцам итог периода не дробится** (Р-12): месяц, покрытый чужим периодом, называет период, а не показывает число. **Покрытым он считается по большинству дней** (Р-20) — край, заходящий на день-другой, месяц не забирает, а задетые дни называются числом. Сопоставимость даёт расход в день, приведённый к `DAYS_IN_MONTH` = 30,44

### Снимки (Р-05, Р-12)

```ts
// Сколько было на счёте на дату. Не `Snapshot`: так в ядре называется файл-копия.
type Balance = Base & {
  accountId: string
  date: string                 // ГГГГ-ММ-ДД
  part?: string                // часть счёта: «карта», «накопительный». Нет — весь счёт
  amount: number               // в валюте счёта, целое; меньше нуля — отложенный платёж (Р-35)
  note?: string
}
```

**На одну дату и счёт — либо снимок без части, либо снимки по частям** (Р-12), вместе они не складываются; итог счёта — сумма частей. Остаток подробнее потока законен: поток и остаток независимы (Р-05).

**Счёт закрывается нулевым снимком и архивом** (Р-44): архивный счёт, у которого последний снимок на дату — ноль, в капитал на эту дату не входит; раньше нуля — считается как был. Архив без нуля деньги не закрывает.

**Кредитка — часть счёта со суммой к возврату, со знаком минус** (Р-35). «Сбережения» показывают деньги как лежат, без неё; отрицательные части идут в капитал своей строкой «Отложенный платёж» и вычитаются.

// Текст, привязанный к модулю и дате: «просад в связи с коррекцией BTC».

type Note = Base & {

```

Хранилище `notes` — вторая миграция схемы, версия 3, `additive: true`.

### Долги — Этап 3 (Р-01, Р-05, Р-30, Р-31, Р-32, Р-33)

```ts
type Person = Base & { name: string; self?: true; archived?: boolean }   // «я» — человек с пометкой

type Room = Base & { name: string; currency: CurrencyCode; personIds: string[]; closed?: boolean }

// Повод, на который скидывались: «Падел, 21 августа». Состав — подмножество комнаты (Р-30).
type RoomEvent = Base & {
  roomId: string
  name: string
  date: string
  personIds: string[]          // кто участвовал: подсказка новой трате, не правило для старых
  closed?: boolean
}

// Кто заплатил, сколько, на кого делится. Доли записаны поимённо в момент заведения (Р-30).
type RoomSpend = Base & {
  eventId: string              // трат вне событий нет
  date: string                 // своя: подставляется из события и дальше живёт сама
  title: string
  payerId: string
  amount: number               // целое в валюте комнаты
  split: { personId: string; share?: number; weight?: number }[]   // суммой или весом (Р-33); нет ни того ни другого — поровну
}

// Кто кому вернул — это и есть «вернул». Принадлежит комнате, а не событию (Р-30).
type RoomTransfer = Base & {
  roomId: string
  date: string
  fromId: string
  toId: string
  amount: number
  note?: string                // «на Сбер» — банк перевода, если назван; справочника банков нет
}

// Одноразовый долг: «дал Пете», «взял у Маши». Без комнаты, события и компании.
type Loan = Base & { personId: string; direction: 'lent' | 'borrowed'; money: Money; date: string; note?: string }
type Repayment = Base & { loanId: string; money: Money; date: string }
```

Шесть условий Р-01 соблюдены: комната самостоятельна и вынимается целиком (`Room` → её `RoomEvent` → их `RoomSpend` плюс `RoomTransfer` комнаты); «я» — участник с пометкой `self`, а не подразумеваемый владелец; каждая трата и перевод — своя запись с `Base`; долги, минимизация переводов и итоги событий считаются, не хранятся; комната не знает про категории и счета учёта — связь идёт со стороны учёта; суммы целые в валюте комнаты.

**Связь с учётом — полем `refs` операции** (Р-31). Есть связь — в поток месяца входит **доля, а не сумма**: у траты комнаты это сумма долей человека с пометкой `self`, у разового долга, возврата и перевода комнаты — ноль. Категория остаётся настоящая: ужин за компанию — «Еда», а не «Долги». Момент задаёт дата операции, а не дата перевода. Лента показывает сумму банка и рядом долю с основанием: «3 000 ₽, своя доля 1 000 ₽ — ужин, комната „Лето“».

### Правила модели

- **Потоки и остатки — два независимых взгляда** (Р-05). Остаток счёта — только снимок; из операций не выводится
- **Долги — не расход и не доход** (Р-05). Операция со связью `refs` входит в поток **долей, а не суммой** (Р-31): у траты комнаты — доли `self`, у долга, возврата и перевода комнаты — ноль. Категория при этом своя, настоящая; момент задаёт дата операции, а не дата перевода
- **Обычный месяц** — средний расход за `USUAL_MONTHS` прошлых месяцев без особых (Р-07). **Норма сбережений** — (доход − расход) / доход; доход не внесён — так и сказано, а не ноль
- **На один счёт в одном периоде — либо итог, либо операции** (Р-02); импорт операций выводит итог и называет разницу
- **Перевод — одна запись, не доход и не расход** (Р-12). Движения внутри одного счёта не записываются вовсе. **Встречные стороны приложение не склеивает** (Р-19): одно движение — одна запись, и пишет её беседа, видящая все выписки сразу; обе стороны описывают его одинаково — `account` откуда, `toAccount` куда. Ошибку ловит сверка (Р-16)
- **Кэшбэк и возврат покупки — доход** отдельными категориями; расход месяца они не уменьшают (Р-12)
- **Всё посчитанное не хранится:** итоги, пересчёты, долги, обычный месяц
- **Стартовых категорий и счетов в коде нет** — у друга свои
- **`refs`** — связи между записями и, позже, между приложениями семьи: строка начинается с вида записи

## Раскладка данных в репозитории

Договор ядра: `meta.json`, справочник — одним файлом, записи — `<папка>/ГГГГ-ММ.json` по дате записи, `undated.json` — без разбираемой даты, `README.md` кладётся ядром (`src/shared/docs/02-Архитектура.md`, «Раскладка репозитория данных»). Своё — `places` конфига:

```
meta.json            { app, schemaVersion } — app: 'zloty', dbName (Я-24)
profile.json         настройки учёта: валюты, период, цель
currencies.json      валюты
accounts.json        счета
categories.json      категории
recurring.json       регулярные
rates/ГГГГ-ММ.json   курсы — по дате курса
entries/ГГГГ-ММ.json операции и итоги периода — по `date`, итог периода — по `period.to`
balances/ГГГГ-ММ.json снимки — по дате
notes/ГГГГ-ММ.json   заметки к капиталу — по дате (Р-36)
README.md
```

Долги — хранилища и строки раскладки миграцией Этапа 3. Нарезка по месяцам: обычный месяц с выпиской — сотни операций, порядка 100 КБ; годовой файл уезжал бы целиком с каждым изменением.

## Хранение на устройстве

База **`zloty`** — свой `dbName` на общем origin `goigolden88.github.io` рядом с `dnevniki`, `deluvremya`, `trapeza` (Р-10). Не меняется никогда.

**`v1Stores` — восемь хранилищ учёта и снимков** (Р-11, Р-12), в этом порядке: `profile`, `currencies`, `accounts`, `categories`, `recurring`, `rates`, `entries`, `balances`. После первого релиза список заморожен. Хранилища долгов — первая миграция, Этап 3; `notes` — вторая, Этап 4 (Р-36).

Индексы сверх `updatedAt`, который ядро заводит само:

| Хранилище | Индексы | Зачем |
|---|---|---|
| `entries` | `date`, `ext`, `accountId` | месяц, ловля повтора при импорте, «что на этом счёте» |
| `balances` | `date`, `accountId` | капитал на дату, история счёта |
| `rates` | `date` | курс на дату и ближайший более ранний |
| остальные | нет | справочники читаются целиком |

**Читать по ним можно — `db.getByIndex` ядра (Я-08), — но пока не читается нигде** (Р-43): всем читателям учёта и курсов нужна вся история, а итог периода хранит `period`, а не `date`, и в индекс даты не попадает. **Индексы заморожены вместе с `v1Stores`** (Я-08): новый индекс — только шагом миграции с `additive: true`, в `config.indexes` не дописывается. Индексов долгов и заметок нет, пока по ним некому читать (Р-32, Р-43).

Локальные хранилища ядра — `meta`, `settings`, `dirty`; `settings` не синхронизируются никогда — там токен. Ключи `settings` — ядра (синхронизация, «Что нового», сворачивание, напоминания, журнал ошибок); свои появятся с поводом и будут записаны здесь.

## Синхронизация

Механика — ядра `FamilyCore` (`shared/core/sync.ts`): local-first, грязные записи, проход через пять секунд после действия, при открытии и возврате сети; сначала влить чужое, потом отправить своё, одним коммитом. **Слияние — по записи, побеждает поздний `updatedAt`**, надгробия не вычищаются (договор семьи). Подключается в Этапе 1 (Р-11).

Файл-копия — механика ядра: `{ schemaVersion, exportedAt, data }`, все синхронизируемые хранилища с надгробиями, `settings` не входит.

## Импорт — договор (Р-08, Р-09)

**Единственная дверь в данные извне.** Любой источник — беседа с Claude сейчас, свой бэкенд или брокер потом — производит этот формат и проходит ту же проверку, сводку и кнопку. Никто не пишет в хранилища и в репозиторий данных напрямую.

```
{ "format": "zloty-import", "version": 1,
  "currencies": [...], "categories": [...], "accounts": [...], "entries": [...],
  "rates": [...], "balances": [...], "notes": [...], "checks": [...] }
```

- Без `id` и `updatedAt`; ссылки — по названиям: счёт, категория, человек. **Недостающая категория заводится, недостающий счёт — нет** (Р-13): у операции нет своей валюты, и выдумать её нельзя; запись называется с причиной, а счёт заводит раздел `accounts`, где валюта сказана явно
- **Суммы — в обычных единицах:** `"amount": 1234.56, "currency": "RUB"`; в минимальные — приложение; лишние знаки округляются и называются в сводке заметкой — «стоит посмотреть», а не отказом
- Каждое поле проверяется; кривая запись не попадает в базу и называется с причиной. До записи — сводка, запись — по кнопке. JSON принимается и в блоке ```` ```json ```` с текстом вокруг — механика ядра
- **Только добавляет**; совпавшее по естественному ключу пропускается. **Исключений два, и оба сводка называет своим словом** (Я-07 ядра): итог периода, который заменяют операции того же счёта и периода, уходит надгробием — «Удалится», разница — заметкой (Р-02); сошедшаяся сверка ставит отметку `loadedThrough` на счёт из базы — «Изменится» (Р-26). Счёт, заведённый этим же файлом, — «Добавится», не правка
- **Исходы разбора — четыре поля `ImportPlan` ядра** (Я-07): `added`, `changed`, `removed` — счётом со склонением; `notes` — загрузится, но стоит посмотреть (округление, замена итога); `issues` — только то, что в базу не попадёт. Что правка и что удаление, говорит приложение: ядро записи с базой не сличает
- **Промпт знает справочники:** текущие категории, счета и регулярные вписываются в промпт из базы; туда же — `PROMPT_SAMPLES` самых частых описаний банков с тем, как они уже разложены по категориям (Р-12)
- **Промпт знает, что уже загружено:** по каждому счёту — дата последней операции, и требование брать выписку **с этого дня включительно**. Повторы отсекает `ext`, а операции, случившиеся после формирования прошлой выписки, приходят (Р-12)
- **Разбор выписки ставит вид записи по описанию:** знак говорит направление; перевод внутри одного счёта не записывается совсем, перевод между своими счетами — записью `transfer`, спорное помечается и попадает в сводку
- **Разделы капитала** — `balances` (счёт по названию, дата, часть, `deferred` для отложенного платежа — сумма без знака; ключ — счёт, дата, часть; на одну дату не смешиваются снимок целиком и по частям; счёт истории снимков не получает) и `notes`. У `currencies` — `unit`, у `rates` — `source`
- **Публичный источник курсов** производит тот же формат: `modules/money/currency-api.ts` отдаёт раздел `rates`, файл идёт через `planImport`, запись — по кнопке после сводки (Р-38). Сводка — `ImportSummary` ядра, та же, что у выписки (Я-07); над ней — что ответил источник и чего у него нет, после записи — куда легли курсы
- **Экран импорта — свой в каждом модуле:** `ImportRecords` ядра с разбором и промптом этого модуля; промпт — `buildPrompt` ядра из разделов модуля (Р-03)
- Разделы разбираются по порядку — справочники, потом записи, — каждый видит заведённое предыдущими
- Операции загружаются на одном устройстве; остальные получают их синхронизацией (Р-21 «Трапезы»)
- Поля и пример каждого раздела — в `modules/<модуль>/import.ts`; из них собирается промпт, тест прогоняет примеры через свою проверку. **Примеры выдуманные:** промпт уезжает к каждому
- **Выписка сверяется по своим же числам** (Р-16): раздел `checks` — счёт, границы периода, `opening`/`closing` и (или) `income`/`expense`, переписанные из выписки. Приложение считает «начало + приход − расход = конец» по записям счёта за период вместе с теми, что уже в базе. **Не сошлось или сверки нет — операции счёта не загружаются,** разница названа суммой; перевод проходит, если сошлась сверка хотя бы одной из сторон. Движения внутри счёта записями не становятся (Р-12, п. 1), но их суммы объявляются полями `skippedIn`/`skippedOut` и входят в остаток; туда же идут операции, чья дата вне периода выписки, — учёт хранит дату операции, а выписка считает по дате обработки (Р-18): выписка приходит на договор, а счёт — банк целиком (Р-17). Остаток главнее оборотов — обороты сверяются, только когда остатков нет. Итоги периодов сверка не трогает — у них нет даты
- **Сверка оставляет след:** у сошедшейся сверки конец периода ложится на счёт полем `loadedThrough` (Р-26). Это единственный источник ответа «по какое число доведена выписка»: из записей он не выводится — счёт, на котором в этом месяце только переводили, по записям выглядит отставшим. Экран «Месяц» берёт наименьшую отметку по живым счетам, кроме счетов истории; счета без отметки срока не задают
- **Формат меняется только добавлением;** старая `version` принимается и после изменений

**История таблицы** — через промпт приложения в сессии Этапа 1, но не из xlsx: файл зашифрован, разбирать нечего. Источник — снимки листов в `seed/`; часть строк человек вносит руками на экранах. Проверка сводит суммы по периодам со столбцом «сумма» таблицы (Р-08, Р-12). История грузится на отдельный счёт с `ledgerOnly`, чтобы её итоги не столкнулись с выписками тех же месяцев. Файлы — только в `seed/`.

**Как файл доезжает до приложения** — вставкой и файлом. «Входящие» в репозитории данных и запрос к брокеру из браузера — решениями, когда появится первый такой источник (Р-09).

## Договор семьи

Живёт в `FamilyCore` (Р-51 «Трапезы»). Чем «Злотые» обязаны: `Base` — из ядра; `FeedItem` — строки ленты собирает `registry.ts`; раскладка — `meta.json`, справочники одним файлом, записи по месяцам, своя таблица `places`; своя `schemaVersion` и миграции. Правка договора — релиз ядра на все приложения, не правка здесь.

**`meta.json` называет приложение** (Я-24): `app` — `dbName`, у «Злотых» `zloty`. Проход, увидевший в репозитории данных чужой `app`, останавливается, ничего не скачав и не отправив, — так ошибка в имени репозитория не сливает данные двух приложений. Давний `meta.json` без `app` принимается, имя дописывается тем же проходом. Подробности — договор ядра, «Раскладка репозитория данных».

**Токен** (Я-25, Я-27) — один fine-grained токен «семья» **на все устройства человека**: Contents: Read and write, только на репозитории данных семьи, без репозиториев кода; вписывается во все приложения на каждом устройстве, «Злотые» работают только с `ZlotyData`. Потерянное устройство — отзыв единственного токена и новый на всех остальных (Я-27, «Цена»); переносится менеджером паролей. «Свой на каждом устройстве» Я-25 отменён Я-27. Переход на него — когда все четыре приложения синхронизировались на ядре с Я-24 и в каждом репозитории данных лежит `app`; до того — прежние токены на один репозиторий. Имя репозитория сверяется кнопкой «Проверить доступ». Договор ядра, «Устройство и origin».

**Срез итогов** (Я-16…Я-21, Я-26) — `summary.json` в репозитории данных, пишет проход функцией `summary` конфига. У «Злотых» функции пока нет — файла нет.

## Версионирование схемы

`schemaVersion` — в `meta.json` рядом с `app` (Я-24; договор ядра, «`schemaVersion`»), с первого дня; миграции пишутся сразу, свежая база доезжает до текущей теми же шагами. Первая миграция — хранилища долгов, Этап 3, `additive: true`; вторая — `notes`, Этап 4, тоже `additive: true`. Устройство на старой версии, увидев схему новее в репозитории, останавливает синхронизацию со словами «обнови приложение».
